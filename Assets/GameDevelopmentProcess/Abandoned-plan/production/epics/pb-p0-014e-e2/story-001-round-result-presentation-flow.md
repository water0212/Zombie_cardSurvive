- ADR Governing Implementation: `Docs/Architecture/adr-0003-morale-preview-and-warning.md`；沿用其 Runtime 權威、UI 唯讀、流程鎖定與輸入隔離原則。

## Scope

建立實際結算完成後的呈現佇列與單次流程交接。呈現順序為其他資源變化、士氣計數、必要的跨階步驟，最後才進入基地崩潰、事件或正常 Gameplay。

## Acceptance Criteria

- [ ] E2-001-01：實際結算依序交付其他資源變化、士氣計數、必要跨階呈現，以及崩潰／事件／正常 Gameplay 出口；沒有跨階時直接略過該步驟。
- [ ] E2-001-02：呈現只讀取已提交的完整交易／輪末結果，不重新計算、重新提交或從最終全域數值倒推來源；遊戲資料每筆交易只提交一次。
- [ ] E2-001-03：結算開始至合法出口接管前維持既有操作鎖定，不以 `Time.timeScale` 取代流程鎖定，手牌、建築、殭屍及時段推進不可操作。
- [ ] E2-001-04：呈現完成訊號只能放行一次；重複回呼、關閉、停用或連續略過不得重複開啟事件、開始下一輪或解除鎖定。
- [ ] E2-001-05：`Failed` 守衛在權威交易確認崩潰時立即生效，後續遊戲邏輯停止；視覺層可等待完整原因就緒，但不得因此延後失敗守衛。
- [ ] E2-001-06：出口優先序固定為崩潰、事件、正常 Gameplay；崩潰時不得先開事件，事件存在時不得短暫恢復 Gameplay 操作。
- [ ] E2-001-07：測試或非正式場景缺少呈現元件時走可控的即時完成路徑，仍遵守相同出口優先序且不造成流程卡死。
- [ ] E2-001-08：定向自動測試涵蓋正常出口、事件出口、崩潰出口、無呈現元件、重複完成訊號與連續略過。

## Implementation Notes

- 以不可變的已提交結果建立呈現工作，不讓 Presenter 成為規則權威。
- 將每個視覺步驟的完成與整條佇列的完成分開；只有佇列完成可以請求流程交接。
- 沿用現有流程鎖定與事件入口，不建立第二套回合或事件狀態機。
- 元件與介面名稱可依現有程式慣例調整，但須保留單次完成與即時完成契約。

## Out of Scope

中央金字塔的最終視覺與動態細節、崩潰畫面的內容排版、Profile 選擇畫面、重新平衡結算數值、完整通知歷史及全 HUD 重製。

## 2026-10-29：明確交易上下文與共用數值動畫（使用者確認）

採用明確交易上下文方案，不以呼叫者身分、同一幀或時間間隔猜測交易邊界。本段為當時確認的設計；目前類別與接口已實作，實際接線與驗證邊界見文末。

- 一次完整出牌、事件選項或輪末由外部權威流程建立交易上下文；該操作的各次資源修改傳遞同一上下文。相同卡牌下一次打出是不同交易。
- 共用數值介面可提供讀取、Set、Change 與變更通知；各系統保留付款、保留量、士氣批次等專用規則。共用介面不代表所有變更必須採同一修改邏輯。
- StateChanged 保留於底層變更通知，不作為本次共用資源數字／增減動畫的觸發入口。需要逐筆追溯的變更結果應包含交易識別、數值識別、來源、前後值與實際變化；成就及統計本體不納入 E2。
- TransactionCompleted 由外部交易擁有者在完整操作結束後發布一次，包含逐項變更與前後快照／實際淨變化，交給資源 UI。Change 不自行宣告整筆交易完成。
- UI 初次綁定、重設或重新開啟直接同步目前快照，不假裝取得資源。卡牌、事件與輪末共用同一資源動畫接口，輪末協調器只安排播放節奏、略過與單次交接。
- 例：支付 2 食物並取得 2 食物，底層保留兩次有效變更，完整結果淨變化 0，UI 不播放淨增減動畫；兩者仍由同一交易識別串起。
- 快照與結果逐筆建立，不使用一份會被下一筆覆蓋的靜態快照；動畫不負責結算或回滾。交易完成通知與演出完成訊號是不同事件。
- 士氣維持完整批次提交及立即 Failed 守衛；交易上下文只串接來源與結果，不將批次拆成逐項不可逆判定，也不延後權威失敗。
- 現有 static Systems 若接入介面，優先以不另存權威數值的轉接物件逐步整合；不在 E2 無差別重寫建築、探索等整個系統。
- 實作需針對重複 Complete、失敗／中斷收尾、巢狀操作邊界及舊局回呼補測；具體策略在實作時定案，不能以本決策宣稱已具備交易回滾或全系統統計功能。

本段記錄當時的設計與實作規劃；目前實作與驗證進度見文末，不以規劃文字宣稱人工驗收通過。
