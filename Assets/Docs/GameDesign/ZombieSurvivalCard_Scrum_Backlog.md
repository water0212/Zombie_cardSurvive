# 殭屍生存卡牌 - Scrum 開發待辦清單

版本：0.4  
日期：2026-08-24  
用途：整理目前已完成、部分完成、尚未完成的開發任務，並依照 Scrum / Backlog 的方式安排優先順序。

這份文件是「開發管理文件」，不是 GDD 的替代品。  
GDD 負責描述遊戲規則與設計意圖；本文件負責描述「接下來要做什麼、先做什麼、怎樣算完成」。

## 產品目標

開發一個可遊玩的垂直切片版本，玩家可以：

1. 透過正規卡組進行回合與輪次循環。
2. 使用卡牌獲得或消耗食物、資源、能量、戰鬥值，之後加入士氣。
3. 在每輪之間處理事件選擇。
4. 使用卡牌倉庫、預設卡與替換系統調整卡組。
5. 面對由殭屍卡產生的殭屍威脅。
6. 在食物、士氣、戰鬥、探索與卡組規劃之間做出生存取捨。

## 優先級說明

- P0：核心循環必須完成，否則遊戲不能穩定測試。
- P1：遊戲主要特色與策略深度所需。
- P2：重要內容、進度系統或中後期功能。
- P3：美術、手感、音效、平衡工具與製作品質。

## 狀態說明

- 已完成：已實作，並且目前可用。
- 部分完成：已有原型，但規則、UI 或整合還不完整。
- 待辦：尚未實作。
- 阻塞：需要先決設計或其他系統完成。

## 完成定義

一個任務要被視為完成，必須符合：

- Unity Play Mode 可以正常運作，沒有 Console 編譯錯誤。
- 必要的 Inspector 欄位與 UI 綁定方式清楚。
- 功能走目前的正式資料流，不依賴一次性的測試捷徑。
- 不破壞既有的打牌、事件、替換、查看牌堆流程。
- 有清楚的手動測試方式。

### PB-P0-009 - 有限地區資料規格與首批數值

狀態：已完成  
優先級：P0  
分類：探索 / 遊戲設計  
設計依據：GDD 第 29.2 至 29.5 節  
目標：為有限地區 Runtime 準備可測試、可比較的首批地區數值，不讓程式完成後仍缺少內容。

使用者故事：
- 身為遊戲設計者，我希望每個地區都有有限卡包、有限殭屍與熱度參數，讓探索的收益、枯竭與風險可以被實際測試。

待做：
- 為廢棄超市、住宅區、消防局、五金行與倉庫建立第一版地區數值表。
- 每個地區填入卡包種類、初始數量、基礎權重、殭屍初始數量、基礎遭遇率、熱度增加量與每日衰減量。
- 定義「充足 / 普通 / 稀少 / 枯竭」與「低 / 中 / 高 / 極高」的顯示門檻。
- 軍事基地保留至有限地區流程驗證完成後再加入正式內容。

- 五個 Demo 地區沒有缺少必要欄位。

- 任一地區都能在有限次探索後枯竭，不存在自然補充來源。
- 數值表不包含專門清理、動態殭屍體質或完整屍群公式。

## 目前最推薦的下一步

PB-P0-014A～D 已完成：士氣已有權威狀態機、統一批次結算、殭屍完整反應窗口、永久上限損傷、可共用的下輪效果，以及資料化 Profile 與整組階段替換。下一個最推薦的開發項目是 PB-P0-014E，補齊玩家可見資訊、預警與失敗回饋。

立即順序：

1. PB-P0-014E：補齊常駐資訊、輪末與跨階預警、局前 Profile 選擇與失敗報告。
2. 進行一輪針對 70／35 門檻、Stage 1 資源壓力與 Stage 2 能量縮減的玩家驗收。

選擇此順序的原因：

- 014A 先建立單一權威狀態機，可避免既有卡牌、事件與輪末流程各自判斷門檻。
- 014B、014C 再逐步遷移來源，較容易發現雙重扣除與結算順序問題。
- 先保證玩家有完整反應窗口，再加入永久損傷，才能讓失敗被理解為準備不足而非無法避免。
- 014D 已把 Profile 與階段效果資料流固定下來；014E 現在可以只處理資訊呈現、選擇與失敗解釋，不必再改動核心結算規則。
